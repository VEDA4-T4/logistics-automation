# 공정 복구 전체 초기화 설계

## 상태

- 결정일: 2026-08-15
- 결정: 비상 복구(`RECOVERY`) 완료 시 중단 지점부터 작업을 재개하지 않는다.
- 적용 기준: #115의 전체 공정 흐름을 유지하되, #127의 단계별 작업 복원과 라인트레이서 즉시 재개 정책은 이 설계로 대체한다.

## 문제

현재 중앙 서버와 노드가 비상 복구의 의미를 다르게 해석한다.

- 중앙 서버는 실패하지 않은 작업을 `STOPPED + suspended_stage`로 남기고 이후 `START`에서 복원한다.
- 일부 노드는 복구 중 진행 중 작업이나 제어 사이클을 초기화한다.
- 라인트레이서는 복구 직후 운송 단계로 복원될 수 있지만, 중앙 시스템은 `STOPPED`일 수 있다.
- 복구 전에 발생한 명령 타임아웃이 `failure_reason`으로 남으면 중앙은 작업을 삭제하지만 노드는 같은 작업을 보존할 수 있다.
- 중앙 DB를 초기화해도 MQTT 영속 세션과 노드 파일 스풀이 남아 과거 공정 메시지가 새 공정으로 유입될 수 있다.

그 결과 작업 ID 대기, 인식 결과 유실, 이미 끝난 명령의 반복 재생, 복구 후 서로 다른 노드 상태가 발생한다.

## 목표

1. 복구 완료 뒤 모든 구성요소가 같은 초기 상태를 갖는다.
2. 복구 이전 작업과 명령은 새 `START` 이후 절대 재개하거나 재발행하지 않는다.
3. 상품 카탈로그만 유지하고 공정 런타임 데이터는 폐기할 수 있다.
4. 정상 공정에서는 투입 정지, 비전 인식, 그리퍼 HOME, 분류 순서를 명확한 완료 신호로 연결한다.
5. 센서 텔레메트리가 제어 명령을 지연시키지 않도록 MQTT 전달 등급을 분리한다.

## 비목표

- 정전이나 프로세스 재시작 뒤 진행 중 작업을 이어서 수행하지 않는다.
- STM32 제어 알고리즘을 변경하지 않는다. 서버와 Pi 노드에서 해결할 수 없는 하드웨어 계약 문제가 확인될 때만 별도 작업으로 분리한다.
- 과거 공정 이력과 migration 적용 이력을 운영 데이터로 보존하지 않는다.

## 확정 복구 계약

### RECOVERY 성공

모든 대상 노드가 안전 복구 성공을 응답한 뒤 중앙 서버는 하나의 원자적 상태 변경으로 다음을 수행한다.

1. 활성 작업을 모두 `FAILED/CANCELLED_BY_RECOVERY` 종결 이벤트 대상으로 만든다.
2. 작업별 미완료 공정 명령, 일반 명령 집계, 복구 전 MQTT outbox/inbox를 폐기한다.
3. 각 노드가 진행 중인 작업, 사이클, 목적지, 임시 인식 결과를 초기화했음을 확인한다.
4. 중앙 공정 상태를 `STOPPED`로 저장한다.
5. 컨베이어와 구동 장치는 정지 상태를 유지한다.
6. 사용자가 새 `START`를 보낼 때만 새 공정을 시작한다.

복구 성공 자체는 `RUNNING`으로 전환하지 않는다. 라인트레이서도 복구 직후 경로를 재개하지 않는다.

### RECOVERY 실패 또는 일부 응답 누락

- 시스템은 `RECOVERY` 또는 `ESTOP` 상태를 유지한다.
- 활성 작업을 재개하지 않는다.
- 성공한 노드만으로 `STOPPED` 완료 상태를 만들지 않는다.
- 누락 장치와 마지막 응답을 Qt에 명시한다.
- 재시도되는 `RECOVERY`는 동일한 초기화 명령이어야 하며 멱등이어야 한다.

### START

- `STOPPED`이며 활성 작업, 보류 공정 명령, 이전 세션 메시지가 없을 때만 허용한다.
- 투입 컨베이어는 시작하고 분류 컨베이어는 정지 상태를 유지한다.
- START는 과거 작업을 복원하지 않고 새 상자 감지를 기다린다.

## 정상 공정 계약

1. `START`: 투입 컨베이어 `RUNNING`, 분류 컨베이어 `STOPPED`.
2. 투입 초음파 또는 비전 상자 감지: 중앙이 작업을 만들고 투입 컨베이어 `STOP`을 발행한다.
3. 투입 정지 성공 뒤 비전에 `WORK_CREATED`를 전달한다.
4. 비전은 위치와 바코드를 독립적으로 누적한다. 동일 상자의 후속 바코드 전용 프레임도 마지막 유효 위치와 결합한다.
5. 바코드와 위치가 준비되면 `POSITION_DETECTED`, `BARCODE_DETECTED`, `PRODUCT_INFO`를 순서대로 내보낸다.
6. 그리퍼가 상자를 집고 HOME 복귀를 완료할 때까지 투입 컨베이어는 정지 상태를 유지한다.
7. 그리퍼 HOME 완료 신호 하나만 공정 완료의 권위 있는 신호로 사용한다.
8. 그리퍼 HOME 완료 뒤 중앙은 분류 목적지를 설정하고 분류 컨베이어를 시작한다. 투입 컨베이어 재시작은 분류 명령 수락 뒤 수행한다.
9. 분류 위치 초음파 감지 시 분류 컨베이어를 정지하고 게이트 분류/복귀를 완료한다.
10. 라인트레이서 사용 구성에서는 분류 완료 뒤 운송을 시작한다. 라인트레이서 제외 구성에서는 작업을 완료한다.

## 비전 처리 규칙

- `IsOperational()` 확인 전에 상태를 소비하는 `TakeAssignedWork()`를 호출하지 않는다.
- 작업 할당, 상자 위치, 바코드는 별도 상태로 보존하고 뒤늦게 도착한 바코드를 결합한다.
- 사전 할당과 바코드 대기는 프레임 수가 아니라 설정 가능한 단조 시계 기반 제한 시간을 사용한다.
- 제한 시간 동안 계속 재시도한다. 만료 시에만 명시적인 `WORK_FAILED`를 내보낸다.
- 결과는 생성 직후 노드의 durable MQTT spool에 기록한다.
- 복구 초기화에서는 workflow, 결과 outbox, 업로드, 캡처, 작업 ID를 모두 폐기한다.

## 명령과 완료 규칙

- 공정 명령별 제한 시간을 분리한다. 범용 3초 제한을 UART 동작 완료 명령에 적용하지 않는다.

| 대상/명령 | 제한 시간 | 근거 |
| --- | ---: | --- |
| input `START` | 5초 | 속도 설정과 시작 UART 왕복 및 MQTT 전달 여유 |
| input `STOP` | 15초 | 실측 11초 완료를 수용하고 스케줄링/전달에 4초 여유 |
| sorting 목적지/`START`/`STOP` | 5초 | 100ms UART ACK 재시도와 2단계 속도 설정/시작 여유 |
| line tracer `EXECUTE`/경로 설정 | 5초 | 100ms UART ACK 재시도와 MQTT 전달 여유 |
| gripper HOME/`INITIALIZE` | 15초 | 10초 HOME 상한, 노드 2초 slack, 전달 여유 3초 |
| gripper `RECOVERY` | 30초 | 안전 해제 후 HOME까지 이어지는 체인 |
| gripper `EXECUTE` | 180초 | 최대 13단계 × (10초 모션 상한 + 2초 노드 slack)와 전달 여유 |
| 그 밖의 짧은 명령 | 3초 | 기존 계약 호환 fallback |

- 명령이 늦게 성공했다고 해서 이미 작업 전체를 실패 처리한 상태와 모순되지 않도록, 타임아웃은 해당 명령 intent에만 기록한다.
- `STOP`, `START`, 목적지 설정, HOME, 분류 완료는 요청 ID와 작업 ID로 멱등 처리한다.
- 그리퍼의 terminal `COMMAND_RESPONSE`를 HOME 완료의 권위 있는 공정 신호로 사용한다.
- 같은 사이클의 후속 `DEVICE_STATUS COMPLETED`는 상태 표시용 중복으로 수용하고 공정 단계를 다시 전이하지 않는다.

## 시작 모드와 저장소

서버 시작 모드는 혼합하지 않는다.

### fresh 모드

- 상품 카탈로그만 보존한다.
- 공정 상태, 작업, 이벤트 inbox, MQTT outbox, 명령 추적, 시스템 명령 집계, 처리된 메시지 ID를 폐기한다.
- DB reset을 migration 검증보다 먼저 수행한 뒤 현재 schema를 새 DB에 적용한다.
- 새 process epoch를 만든다.
- 이전 epoch의 공정 메시지와 명령 응답을 거부한다.
- 노드 초기화를 완료하고 `STOPPED`에서 대기한다.

### resume 모드

- DB, inbox, outbox, 명령 추적을 그대로 복원한다.
- 같은 process epoch만 재생한다.
- 이 모드는 향후 명시적으로 선택할 때만 사용하며, 현재 통합 시험 기본값은 `fresh`다.

중앙 DB만 초기화하고 MQTT persistent session은 재사용하는 구성은 허용하지 않는다. process epoch를 중앙 명령과 노드 공정 이벤트에 포함해 이전 세션 메시지를 식별한다. 작업 ID가 없는 센서 텔레메트리는 epoch와 무관한 현재 측정값으로만 처리하며 작업 생성 에지는 새 START 이후 입력 안정화 조건을 만족해야 한다.

## MQTT 전달 등급

- `SENSOR_STATUS`: QoS 0, non-retained, non-durable. 최신값만 Qt와 감지기에 반영한다.
- 작업 생성 에지, 제어 명령, 명령 응답, 위치/바코드/상품/완료/오류: QoS 1, durable.
- heartbeat: QoS 0. Qt의 상대 시간은 장치 timestamp가 아니라 중앙 수신 시각을 사용한다.
- `WORK_CREATED`는 vision의 `WORK_ASSIGNED(workId)` 응답까지 중앙 outbox에서 제거하지 않는다.
- durable replay는 process epoch와 작업 ID가 현재 상태에 맞을 때만 실행한다.

## #115 및 #127 호환성

- #115의 전체 공정 순서와 노드 역할은 유지한다.
- #127의 비전 사전 할당 제한 시간과 실패 발행 의도는 유지하되 wall-clock 기반으로 바꾼다.
- #127의 실패 완료 이벤트 선발행은 모든 활성 작업을 복구 취소로 종결하는 방식으로 일반화한다.
- #127의 라인트레이서 운송 단계 즉시 복원과 suspended stage 재개는 제거한다.

## 검증 기준

### 공정

- 센서 감지와 비전 감지 각각으로 투입 정지가 발생한다.
- 바코드 전용 후속 프레임으로 인식이 완료된다.
- 그리퍼 HOME 전에는 투입 START가 발행되지 않는다.
- 그리퍼 HOME 뒤 분류 목적지와 분류 START가 먼저 수락되고 투입 START가 발행된다.
- 분류 초음파 감지 뒤 분류 STOP과 게이트 복귀가 완료된다.
- 라인트레이서 포함/제외 경로가 각각 완료된다.

### 복구

- 모든 공정 단계에서 ESTOP 후 RECOVERY 성공 시 활성 작업과 pending 명령이 0개다.
- 모든 노드는 정지/초기 상태이고 중앙은 `STOPPED`다.
- START 전 이전 `WORK_CREATED`, 경로, 그리퍼/분류 명령이 재발행되지 않는다.
- 새 START 뒤 새 작업 ID만 생성된다.
- 일부 노드 복구 실패 시 초기화 완료로 표시하지 않는다.

### 저장소와 MQTT

- fresh 시작 후 카탈로그만 남는다.
- 이전 epoch의 broker queued message와 노드 spool message가 새 작업을 만들지 않는다.
- resume 모드는 같은 epoch의 미완료 QoS 1 메시지만 재생한다.
- 센서 폭주가 명령 응답과 heartbeat를 지연시키지 않는다.
- 프로세스 중단/PUBACK 지연/재연결 테스트에서 제어 및 완료 이벤트가 유실되지 않는다.

## 배포 범위

- 중앙 서버: 상태 머신, 저장소 초기화 순서, command timeout, MQTT epoch/replay, 공정 dispatch.
- 공통 계약: process epoch와 메시지 검증.
- Pi 공통 MQTT: sensor QoS 분리와 epoch 전달.
- vision 노드: 비전 상태 결합, wall-clock timeout, 복구 전체 초기화.
- gripper/sorting/input/line tracer 노드: 초기화 멱등성과 완료 중복 처리 확인 및 필요한 최소 변경.
- STM32: 변경하지 않는다. UART 계약이 현재 노드 동작을 충족하지 못한다는 실측 증거가 있을 때만 별도 변경한다.
