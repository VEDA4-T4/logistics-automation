# 라인트레이서 비상정지 복구 재개 설계

## 목적

비상정지 후 `RECOVERY`가 성공하면, 라인트레이서가 이미 적재해 운송 중이던 단일 작업만 기존 경로에서 재개한다. 입력, 비전, 그리퍼, 분류의 미완료 작업은 기존 규약대로 복구 취소한다.

## 범위

- 변경 대상은 중앙 서버뿐이다.
- 라인트레이서 Pi와 STM32의 UART/MQTT 계약은 변경하지 않는다.
- 최초 기동과 실제 `POSITION_UNKNOWN`의 `INITIALIZE(currentPosition=A)` 동작은 그대로 둔다.
- 라인트레이서 Pi 또는 STM32가 재부팅되었거나 UART 상태가 복구되지 않은 경우에는 재개하지 않는다.

## 현재 원인

중앙 서버가 시스템 `RECOVERY`를 모든 노드로 보내면 라인트레이서 Pi는 `UART_CMD_RESET_DEVICE`를 수행하고 활성 작업과 경로를 지운다. 이어서 중앙 서버의 `CompleteSystemRecovery()`도 모든 활성 작업을 삭제하고 `CANCELLED_BY_RECOVERY`를 발행한다. 따라서 노드 전송만 제외해도 중앙의 운송 작업이 사라져 재개할 수 없다.

## 복구 규칙

1. 중앙 서버는 `EMERGENCY_STOP`에서 시작한 시스템 `RECOVERY`만 재개 후보를 평가한다.
2. 후보는 `suspended_stage == TRANSPORTING`이고 마지막 운송 상태가 라인트레이서에서 보고된 작업이다. 후보가 정확히 하나일 때만 보존한다.
3. 후보가 있으면 라인트레이서를 시스템 `RECOVERY` 대상에서 제외한다. 나머지 등록 노드는 기존 `RECOVERY`를 수행한다.
4. 복구 완료 시 보존 후보만 `TRANSPORTING` 상태로 되돌리고, 다른 미완료 작업은 `CANCELLED_BY_RECOVERY`로 종결한다. 중앙 공정 상태는 `RUNNING`으로 전환한다.
5. 중앙 서버는 보존한 work ID를 포함한 단일 `START`를 라인트레이서에 durable MQTT 명령으로 전송한다. 이는 Pi의 기존 `RESUME_DRIVE` 경로를 사용하며 목적지 설정을 재전송하지 않는다.
6. `START`가 성공 또는 중복 성공이면 라인트레이서 상태/완료 이벤트를 평소처럼 처리한다. 전송·응답 실패면 보존한 작업을 실패 처리하고 시스템을 오류 상태로 전환한다.
7. 후보가 없거나 후보가 둘 이상이면 기존 전체 초기화 복구를 수행한다. 둘 이상은 어떤 경로를 재개할지 추측하지 않는다.

## 상태 및 영속성

- 복구 응답이 모두 성공하기 전에는 기존처럼 `RECOVERY`와 `RECOVERING` 상태를 유지한다.
- 복구 완료와 보존 작업 상태, 라인트레이서 `START` 명령 추적/outbox는 한 번의 저장 경로에서 지속화한다. 서버가 명령 전송 직후 재시작해도 재개 명령은 기존 durable outbox 규칙으로 재생된다.
- 취소되는 작업의 실패 완료 이벤트만 발행한다. 보존 작업에는 `CANCELLED_BY_RECOVERY`를 발행하지 않는다.

## 안전 경계

- `POSITION_UNKNOWN`, 라인트레이서 오프라인, 오류 상태, 재부팅, UART 미연결은 자동 재개 조건이 아니다. 이 경우 기존 초기화 절차를 사용한다.
- 시스템 오류에서 시작한 일반 `RECOVERY`는 기존 전체 초기화 복구를 유지한다.
- 운송 중이 아닌 작업은 재개하지 않는다.

## 검증

- 운송 중 ESTOP → RECOVERY: 라인트레이서는 `RECOVERY`를 수신하지 않고, 다른 노드 복구 성공 후 한 번의 `START(workId)`를 수신한다.
- 보존 work는 `TRANSPORTING`에서 라인트레이서 완료 이벤트를 받아 `COMPLETED`로 전이하며 취소 이벤트가 없다.
- 운송 work가 없는 ESTOP 복구와 일반 오류 복구는 기존처럼 모든 활성 작업을 취소한다.
- 라인트레이서 재개 명령 실패는 작업과 시스템을 안전 오류 상태로 만든다.
