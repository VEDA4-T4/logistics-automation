# 통신 계약 버전 및 변경 관리

이 문서는 `shared/contracts`에서 관리하는 MQTT, UART 및 HTTP(S) 통신 계약의 버전 형식과 변경 절차를
정의합니다. 모든 송신자와 수신자는 배포 전에 이 정책과 공통 계약 테스트를 기준으로 호환성을 확인해야 합니다.

## 현재 버전

| 계약 | 현재 버전 | 코드 기준 | 표현 방식 |
| --- | --- | --- | --- |
| MQTT | `1.0` | `mqtt::kCurrentProtocolVersion` | JSON 문자열 `MAJOR.MINOR` |
| UART | `0x01` | `UART_PROTOCOL_VERSION` | 프레임의 1-byte `VERSION` |
| HTTP(S) | `v1` | `/api/v1/...` | URL 경로의 정수 `MAJOR` |

현재 MQTT codec은 `protocolVersion`의 정확한 일치를 요구합니다. 따라서 호환 가능한 변경이라도 버전을 올리려면
모든 MQTT 송수신 구성요소가 새 버전을 처리하도록 먼저 배포해야 합니다. 같은 규칙을 UART와 HTTP(S)의 버전 변경에도
적용합니다.

## 버전 형식

### MQTT

- `MAJOR.MINOR` 형식의 10진수 문자열을 사용합니다.
- `MAJOR`는 기존 송수신자가 해석할 수 없는 비호환 변경에서 증가시킵니다.
- `MINOR`는 같은 `MAJOR` 안에서 기능을 확장하면서 새 버전 식별이 필요한 경우 증가시킵니다.
- 현재처럼 codec이 정확한 버전만 허용할 때는 단순 선택 필드 추가만으로 버전을 변경하지 않습니다.

### UART

- 프레임의 `VERSION`은 1-byte 정수이며 현재 값은 `0x01`입니다.
- 선택적인 새 명령 ID 추가처럼 기존 프레임 해석에 영향을 주지 않는 변경은 버전을 유지합니다.
- 헤더 배치, CRC 범위, 바이트 순서 또는 기존 payload 구조가 바뀌면 버전을 증가시킵니다.
- 기존 명령 ID를 다른 의미로 재사용하지 않습니다.

### HTTP(S)

- API의 주 버전은 URL 경로에 `/api/v{MAJOR}` 형식으로 표시합니다.
- 선택 필드나 새 endpoint 추가는 기존 `v1`을 유지할 수 있습니다.
- 기존 endpoint, 필수 필드, 인증 또는 응답 의미가 호환되지 않게 바뀌면 새 주 버전 경로를 추가합니다.

## 변경 분류

### 호환 변경

다음 변경은 기존 수신자가 메시지를 계속 처리할 수 있을 때 호환 변경으로 간주합니다.

- 선택 필드 추가
- 새 MQTT message type, UART command ID 또는 HTTP endpoint 추가
- 기존 의미와 범위를 바꾸지 않는 문서 설명 및 검증 강화
- 기존 오류 코드의 의미를 바꾸지 않는 새 오류 코드 추가
- 기존 제한을 유지하거나 완화하는 변경

새 enum 값이나 message type을 추가할 때 수신자가 알 수 없는 값을 안전하게 거부하거나 무시할 수 있는지 반드시
확인합니다. 그렇지 않으면 비호환 변경으로 처리합니다.

### 비호환 변경

다음 변경은 주 버전을 증가시키거나 명시적인 전환 기간을 두어야 합니다.

- 필수 필드 추가, 기존 필드 삭제 또는 이름 변경
- 필드 타입, 단위, 허용 범위 또는 의미 변경
- MQTT topic 구조, QoS 또는 retain 의미 변경
- UART 헤더, CRC, 바이트 순서, 기존 command ID 또는 payload 구조 변경
- HTTP endpoint 삭제, 인증 방식 변경 또는 성공·오류 응답 의미 변경
- 기존 상태, 명령 또는 오류 코드의 의미 재사용

## 폐기 절차

기존 필드, 명령 또는 endpoint를 즉시 삭제하지 않습니다.

1. 계약 문서와 코드에서 폐기 예정 항목을 `deprecated`로 표시합니다.
2. 대체 항목과 전환 방법을 문서화하고 Jira 변경 이슈에 영향받는 구성요소를 기록합니다.
3. 가능한 경우 전환 기간 동안 구형·신형 형식을 함께 읽되 송신은 신형 형식만 사용합니다.
4. 모든 송수신 구성요소의 전환과 통합 테스트가 끝난 후 제거합니다.
5. 병행 지원이 불가능하면 구형 형식을 수정하지 않고 새 주 버전을 추가합니다.

## 변경 절차

통신 계약을 변경할 때 다음 순서를 따릅니다.

1. 변경 목적, 호환성 분류와 영향받는 노드를 Jira 이슈에 기록합니다.
2. `shared/include/logistics/contracts`의 타입·상수와 `shared/contracts`의 codec·parser를 먼저 수정합니다.
3. MQTT, UART 또는 HTTP(S) README와 이 문서의 현재 버전·변경 이력을 함께 갱신합니다.
4. 정상 왕복, 구버전 입력, 알 수 없는 값, 누락 필드와 오류 입력에 대한 계약 테스트를 추가합니다.
5. 중앙 서버, 장치 Raspberry Pi, STM32와 Qt 관제 프로그램의 소비 코드를 수정합니다.
6. 공통 계약 테스트와 영향받는 구성요소의 단위·통합 테스트를 통과시킵니다.
7. PR 설명과 Jira 이슈에 호환성 판단, 테스트 결과와 배포 순서를 남깁니다.
